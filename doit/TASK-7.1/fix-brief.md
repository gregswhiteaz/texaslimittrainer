## 1. [MAJOR] src/advice/equity.ts:unbounded-feasibility-backtrack (security review)
- Where: src/advice/equity.ts:279
- Problem: On the sampled path, the check that a full deal exists (table.forEachDeal(0, () => true)) is a backtracking search with no work limit. When the ranges cannot all be dealt but each range on its own is large, the search tries every partial deal before it fails. That is exponential in the number of opponents, and it happens before the rejection cap or any other bound applies. computeEquity is synchronous and meant for the bot's 100 ms decision budget and the hint path on the main thread, so a bad range set freezes the app. This contradicts spec section 8, which says work per call is bounded by the opponent limit, the exact-evaluation limit, the trial count and the rejection cap. The builder followed the spec's design (section 5, step 5), so the gap is in the spec as well as the code.
- Evidence: Input: opponent ranges from future advice or bot code (range narrowing). The trust boundary is internal, but faulty input is realistic here. Path: computeEquity -> canonicalise -> estimateEvaluations > 200,000 -> sampledEquity -> table.forEachDeal(0, () => true) -> recursive backtracking with no budget. Reproduced: hero Ah Kh, board Qh Jh Th, and 8 opponents, each with every combo of the 15 remaining T-A cards (105 combos each, 16 cards needed, 15 available). This had not finished after 60 s and was killed. The same ranges with 7 opponents return in about 106 ms, because the rejection cap throws. The search space is about 15!/2^7, roughly 1e10 partial deals.
- Expected fix: Give the feasibility search a budget. For example, count visited nodes in forEachDeal, stop after a fixed limit such as 100,000, and treat the result as 'unknown'. Then continue to rejection sampling, where maxRejections already bounds the work and throws. Optionally add a cheap early check first: if the union of cards across the live ranges has fewer than 2k cards, throw cannotDeal() straight away. A full search or a bipartite-matching check is only exact for some cases, so the budget is still needed. Add a SPEC-10 style test with the infeasible 8-opponent broadway case and assert that it throws a RangeError quickly. Update spec sections 5 and 8 to match.
